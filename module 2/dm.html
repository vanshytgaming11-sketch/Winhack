Module 2.1 — Dynamic Memory

So far, all variables have lived on the stack — memory automatically managed by the compiler, allocated when a variable comes into scope and freed when it goes out of scope. C++ also allows explicit, manual control over a second memory region called the heap, using new and delete. This gives you memory that persists beyond the function that created it — but with that power comes full responsibility for cleaning it up.

1. Stack vs Heap

AspectStackHeap
AllocationAutomatic (compiler-managed)Manual (new / delete)
LifetimeTied to scope — destroyed when block/function exitsPersists until explicitly deleted
SpeedVery fast (just pointer bump)Slower (involves memory manager bookkeeping)
SizeLimited (typically a few MB, fixed at program start)Much larger, limited by available system memory
ManagementAutomatic — no leaks possibleManual — leaks and dangling pointers possible if mismanaged
Typical useLocal variables, function parametersData whose size/lifetime isn't known at compile time
 
void demo() {
    int a = 10;          // STACK — destroyed automatically when demo() returns
    int *p = new int(20); // HEAP — the int(20) persists after demo() returns,
                            // UNLESS explicitly deleted (memory leak if forgotten)
}

2. Allocating Memory with new

int *p = new int;        // allocates a single uninitialized int on the heap
int *p2 = new int(42);     // allocates and initializes to 42
int *p3 = new int{42};      // brace-initialization (C++11+, preferred — prevents narrowing)

cout << *p2;                   // 42

double *d = new double(3.14);
cout << *d;                       // 3.14

new returns a pointer to the newly allocated memory. Unlike a local variable, this memory does NOT disappear when the current function returns — it remains reserved until explicitly freed with delete.

3. Freeing Memory with delete

int *p = new int(42);
cout << *p;    // 42
delete p;        // frees the memory back to the system
// p still holds the OLD address here — using *p now is undefined behavior (dangling pointer, see below)

Best practice — null the pointer after deleting:

int *p = new int(42);
delete p;
p = nullptr; // now safe to check `if (p == nullptr)` before any future use

4. Dynamic Arrays

int *arr = new int[5];         // allocates an array of 5 uninitialized ints on the heap
int *arr2 = new int[5]{1,2,3,4,5}; // allocates and initializes (C++11+)
int *arr3 = new int[5]();          // allocates and zero-initializes every element

for (int i = 0; i < 5; i++) {
    arr[i] = i * 10;
}

for (int i = 0; i < 5; i++) {
    cout << arr[i] << " ";
}
// 0 10 20 30 40

delete[] arr;   // MUST use delete[] (with brackets) for arrays — see below
delete[] arr2;
delete[] arr3;

Critical rule — matching new/delete forms:

Allocated withMust free with
new Typedelete ptr;
new Type[n]delete[] ptr;
 
int *arr = new int[10];
delete arr;    // WRONG — using delete (no brackets) on an array is undefined behavior:
                  // it may only destroy/free the first element's worth of memory,
                  // leaking the rest, or corrupting the heap.
delete[] arr;    // CORRECT

5. Dynamic 2D Arrays

int rows = 3, cols = 4;

// Allocate an array of row-pointers, then allocate each row separately
int **matrix = new int*[rows];
for (int i = 0; i < rows; i++) {
    matrix[i] = new int[cols];
}

// Use it like a normal 2D array
for (int i = 0; i < rows; i++) {
    for (int j = 0; j < cols; j++) {
        matrix[i][j] = i * cols + j;
    }
}

// MUST free in reverse order — each row first, then the row-pointer array
for (int i = 0; i < rows; i++) {
    delete[] matrix[i];
}
delete[] matrix;

Freeing matrix before freeing each matrix[i] would leak every row's memory, since you'd lose the only pointers referencing them.

6. Memory Leaks

A memory leak occurs when heap memory is allocated but never freed, and the program loses all pointers to it — making it permanently unreachable and unrecoverable until the program exits. 

void leak() {
    int *p = new int(5); // allocated
    // function ends WITHOUT delete — p (the only reference to this memory) is destroyed,
    // but the memory itself is NOT freed. This block is now leaked forever
    // (until the OS reclaims it when the whole process exits).
}

int main() {
    for (int i = 0; i < 1000000; i++) {
        leak(); // leaks a small block on every call — over time, this exhausts available memory
    }
    return 0;
}

Another common leak — overwriting a pointer before freeing it:

int *p = new int(10);
p = new int(20);  // The original block (holding 10) is now leaked —
                     // its address is gone, no way to delete it anymore
delete p;             // only frees the SECOND allocation

7. Dangling Pointers

A dangling pointer is one that still holds the address of memory that has already been freed (via delete) or has otherwise gone out of scope. Dereferencing it is undefined behavior — it might crash, silently corrupt data, or appear to "work" while being fundamentally unsafe. 

int *p = new int(42);
delete p;
cout << *p; // UNDEFINED BEHAVIOR — p is a dangling pointer, the memory it points to
              // has been returned to the system and may be reused for something else

Another common dangling pointer scenario — returning the address of a local (stack) variable:

int* createDangling() {
    int local = 100;
    return &local; // DANGEROUS — local is destroyed when the function returns
}

int main() {
    int *p = createDangling();
    cout << *p; // UNDEFINED BEHAVIOR — p points to stack memory that no longer belongs to `local`
    return 0;
}

Fix: either return by value (a copy), or allocate with new if the data genuinely needs to outlive the function (and remember to delete it eventually, or better — use a smart pointer, covered in Module 5.3).

8. Double-Free (another classic bug)

int *p = new int(5);
delete p;
delete p; // UNDEFINED BEHAVIOR — freeing already-freed memory corrupts heap bookkeeping structures

This is why setting a pointer to nullptr right after delete is good practice — delete nullptr; is explicitly guaranteed safe (a no-op) by the C++ standard, so accidental double-deletes on a nulled pointer are harmless.

9. Summary — Rules to Avoid Memory Bugs

  • Every new must have exactly one matching delete (or new[] with exactly one delete[]).
  • Never use memory after delete-ing it.
  • Never delete the same pointer twice.
  • Set pointers to nullptr after deleting them.
  • Never return the address of a local (stack) variable from a function.
  • In modern C++, prefer smart pointers (unique_ptr, shared_ptr — Module 5.3) which automate this entirely and eliminate these bug classes.

Practice Questions

Conceptual

  1. Explain the difference between stack and heap memory in terms of lifetime, speed, and management.
  2. What is a memory leak? Give an example scenario (other than "forgetting delete") where a leak can occur even though delete is called somewhere in the program.
  3. What is a dangling pointer? Describe two distinct ways a pointer can become dangling.
  4. Why must delete[] be used for arrays instead of plain delete? What can go wrong if you mismatch them?
  5. Why is delete p; delete p; dangerous, and how does setting p = nullptr; after the first delete help?

Predict/Identify the Bug

delete arr;
    What's wrong here? 
  3. int *p = new int(5);
p = new int(10);

    Identify the bug and explain its consequence.

Coding

  1. Write a program that dynamically allocates an array of n integers (n read from user input), fills it with values, prints the sum, and properly frees the memory.
  2. Write a program that dynamically allocates a 2D matrix of size rows x cols (both read from input), fills it with the product i*j, prints it, and correctly frees all allocated memory.
  3. Write a function int* copyArray(int arr[], int size) that dynamically allocates a new array, copies all elements from arr into it, and returns the new array's pointer. Demonstrate correct usage (and cleanup) in main().
  4. Write a program that deliberately demonstrates a memory leak in a comment-annotated function, then show the corrected version with proper delete.
