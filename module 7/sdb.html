Module 7.4 — System Design Basics (Optional)

This sub-topic is explicitly optional for the fresher/intern track — as noted in the original syllabus, it's only relevant if targeting SDE-2+ roles or backend-heavy positions where a system design round is likely. If your interview pipeline is purely DSA-focused (common for fresher and intern hiring), this can be safely skipped or deferred. It's included here as a brief orientation in case it becomes relevant later.

1. How System Design Differs from DSA Interviews

AspectDSA interview (Modules 6–7.1–7.3)System design interview
GoalProduce a correct, efficient algorithm for a well-defined problemDesign a scalable, reliable architecture for an ambiguous, open-ended problem
CorrectnessUsually a single correct answer (or a small set of optimal approaches)Many reasonable designs exist — evaluated on tradeoffs and justification, not a single "right" answer
Time scaleMilliseconds to seconds (algorithm runtime)Requests per second, storage growth over months/years, geographic latency
Typical duration30–45 minutes, one problem45–60 minutes, one open-ended system

2. Core Vocabulary (Orientation Only — Not a Full Treatment)

TermBrief meaning
Load balancerDistributes incoming requests across multiple servers to avoid overloading any single one
Horizontal vs vertical scalingHorizontal: adding more machines. Vertical: making one machine more powerful
CachingStoring frequently accessed data in fast-access memory to reduce load on slower underlying storage
Database shardingSplitting a database across multiple machines, each holding a portion of the data
CAP theoremA distributed system can only guarantee two of Consistency, Availability, and Partition tolerance at once
Latency vs throughputLatency: time for one request to complete. Throughput: total requests handled per unit time

3. A Rough Approach Structure (If This Round Applies to You)

  1. Clarify requirements — functional (what must the system do) and non-functional (how many users, how much data, read-heavy or write-heavy, consistency requirements).
  2. Estimate scale — rough back-of-envelope numbers for requests/second, storage growth, bandwidth — this shapes every subsequent decision.
  3. Sketch a high-level design — the major components (clients, load balancer, application servers, database, cache) and how data flows between them.
  4. Deep-dive on 1–2 components — the interviewer usually steers this; go deeper on whichever piece is most interesting or most load-bearing for the system's core requirement.
  5. Discuss tradeoffs — explicitly name what you're optimizing for and what you're sacrificing (e.g., "I'm choosing eventual consistency here to prioritize availability, since [reasoning]").

4. Why This Module Stays Brief Here

System design is a large enough discipline that it warrants its own dedicated resource, not a single sub-topic tacked onto a DSA-focused syllabus — this section exists only to orient you on whether/when to seek that out, not to replace it. Given your current focus on DSA interview prep for fresher/intern roles (per your syllabus notes), this is correctly deprioritized until it becomes relevant to your specific interview pipeline.
