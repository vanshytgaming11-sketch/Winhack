Module 7.2 — Mock Interviews

A mock interview simulates the real conditions of a technical interview: a single problem, a hard time limit, verbalized reasoning, and follow-up questions — conditions that practicing alone, untimed, in silence, does not replicate. This module provides the structure to run one, either solo (narrating out loud) or with a partner.

1. The 45-Minute Structure

PhaseDurationWhat happens
Problem introduction2 minRead the problem statement once, ask clarifying questions (input size? duplicates allowed? negative numbers?)
Approach discussion5–8 minTalk through your approach OUT LOUD before coding — state the pattern, the target complexity, and any edge cases you're already anticipating
Coding20–25 minWrite the solution while continuing to narrate your reasoning — treat silence as a red flag, not a neutral state
Testing5 minTrace through your code manually on the given example AND at least one edge case
Follow-up questions5–10 minAnswer "what if the input were 10x larger," "can you reduce the space complexity," "what if X constraint changed"

2. Why Verbalizing Matters — More Than It Seems

Interviewers evaluate communication as much as correctness. A candidate who silently produces a correct O(n) solution often scores WORSE than one who talks through a slightly slower approach first, explains the tradeoff, and then optimizes — because the interviewer needs to see your reasoning process to evaluate how you'd perform on a team, not just whether you can produce correct code.

Practical habit to build: narrate in this shape, consistently:

  • "My first instinct is a brute-force approach that does X — that would be O(n²)."
  • "But I notice [property of the input] — that suggests I could use [pattern] instead, bringing it down to O(n log n) / O(n)."
  • "Let me code that up." (then narrate key decisions while typing, not everything)
  • "Let me trace through the example to check this works... [walk through it]."
  • "One edge case I should consider is [X] — let me verify that's handled."

3. Common Follow-Up Question Types (and how to prepare for them)

Follow-up typeExampleWhat it's testing
Scale-up"What if the array had 10 billion elements and didn't fit in memory?"Whether you understand your solution's actual bottleneck, and can reason about streaming/external approaches
Constraint change"What if the array could contain duplicates?" / "What if it's not sorted anymore?"Whether your solution's correctness genuinely depended on an assumption you may not have stated explicitly
Space optimization"Can you do this in O(1) extra space?"Whether you can identify and eliminate unnecessary auxiliary structures (recall Module 6.10's space-optimized DP)
Generalize"What if we needed the K-th such answer, not just the first?"Whether your approach is a one-off trick or built on a genuinely extensible pattern

4. Running a Mock Interview Solo

Without a partner, discipline substitutes for the interviewer's presence:

  1. Pick a problem you have NOT seen before (or haven't looked at in months) — familiarity defeats the exercise's purpose.
  2. Set a hard timer. Do not pause it, even to "just think for a second" past the phase's allotted time.
  3. Actually speak out loud, even alone — silently thinking through an approach exercises a different skill than articulating it in real time, and the gap between the two is exactly what mock interviews are meant to close.
  4. Write your own follow-up questions in advance (sealed in a separate note) and open them only after your working solution is complete, to simulate not knowing what's coming.

5. Post-Interview Self-Review Template

Immediately after each mock interview (not days later, while details are still fresh), record:

  • Pattern identified: which Module 6 sub-topic did this problem draw from?
  • Time to first working approach: how many minutes elapsed before you had ANY correct-direction idea, even if suboptimal?
  • Time to optimal complexity: did you reach the best achievable complexity, and if not, what did you miss?
  • Communication gaps: were there moments of silence longer than ~30 seconds? What were you thinking during them that went unspoken?
  • Follow-up performance: which follow-up questions did you answer confidently vs. struggle with?

This log is the direct input to Module 7.3 — weak-area review only works if there's an honest record of where the actual gaps showed up, not a vague impression of "it went okay."

Practice Questions

This sub-topic has no separate practice problems — instead, run at least 3 full mock interviews using problems from Module 7.1's practice sets (ones you haven't already solved in that context), following the 45-minute structure above, and complete the self-review template after each one before proceeding to Module 7.3.
