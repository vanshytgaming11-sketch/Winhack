Module 3.2 — Exception Handling

Exception handling is a mechanism for detecting and responding to runtime errors in a controlled way, separating error-detection code from error-handling code. Instead of a function failing silently or crashing the whole program, it can throw an exception that gets caught and handled at an appropriate point up the call stack.

1. try, throw, catch

int divide(int a, int b) {
    if (b == 0) {
        throw runtime_error("Division by zero!"); // throws an exception object
    }
    return a / b;
}

int main() {
    try {
        int result = divide(10, 0);   // this line throws
        cout << result;                 // never reached — control jumps straight to catch
    } catch (const runtime_error &e) {
        cout << "Caught exception: " << e.what() << endl;
    }
    cout << "Program continues normally" << endl;
    return 0;
}
// Output:
// Caught exception: Division by zero!
// Program continues normally

How it works:

  • try — wraps code that might throw an exception.
  • throw — signals that an error occurred, and "throws" an exception object (any type — a string, an int, a custom class, or a standard exception type).
  • catch — catches and handles an exception of a matching type, thrown anywhere within the corresponding try block (including inside functions called from it).

When an exception is thrown, normal execution stops immediately at that point, and control jumps directly to the nearest matching catch block — skipping all remaining code in the try block and any intermediate function calls (this unwinding process is called stack unwinding).

2. Standard Exception Types

C++ provides a hierarchy of standard exception classes in <stdexcept>, all deriving from std::exception. Using these (rather than throwing raw strings/ints) is best practice, since they all support a uniform .what() method describing the error.

Exception typeTypical use
std::runtime_errorErrors detectable only at runtime (e.g., invalid input, external failure)
std::logic_errorErrors from flawed program logic (theoretically preventable)
std::invalid_argumentAn argument doesn't meet expected criteria
std::out_of_rangeAccessing an index/element outside valid bounds (e.g., thrown by vector::at(), string::at())
std::bad_allocThrown automatically by new when memory allocation fails
std::exceptionBase class of all standard exceptions — can catch anything derived from it
 
#include <stdexcept>
using namespace std;

int main() {
    vector<int> v = {1, 2, 3};
    try {
        cout << v.at(10);   // out of bounds — .at() throws, unlike v[10] which is undefined behavior
    } catch (const out_of_range &e) {
        cout << "Error: " << e.what() << endl;
    }
    return 0;
}

3. Multiple catch Blocks

A single try block can be followed by multiple catch blocks, each handling a different exception type. They're checked top to bottom, and only the first matching one executes.

void process(int code) {
    if (code == 1) throw invalid_argument("Invalid input");
    if (code == 2) throw out_of_range("Value out of range");
    if (code == 3) throw runtime_error("General runtime error");
    throw 42; // throwing a plain int — also legal, though not best practice
}

int main() {
    for (int i = 1; i <= 4; i++) {
        try {
            process(i);
        } catch (const invalid_argument &e) {
            cout << "Invalid argument: " << e.what() << endl;
        } catch (const out_of_range &e) {
            cout << "Out of range: " << e.what() << endl;
        } catch (const runtime_error &e) {
            cout << "Runtime error: " << e.what() << endl;
        } catch (int code) {
            cout << "Caught raw int: " << code << endl;
        }
    }
    return 0;
}

Catch-All Handler — catch (...)

try {
    // risky code
} catch (const exception &e) {
    cout << "Standard exception: " << e.what() << endl;
} catch (...) {     // catches literally ANYTHING not matched above
    cout << "Unknown exception caught" << endl;
}

catch (...) doesn't give you access to the exception's value/type — it's a last-resort safety net, often used at a program's outermost boundary to guarantee nothing escapes unhandled.

Ordering Matters — Catch Derived Before Base

try {
    throw out_of_range("test");
} catch (const exception &e) {         // out_of_range IS-A exception — matches FIRST if placed first
    cout << "Generic: " << e.what();
} catch (const out_of_range &e) {        // UNREACHABLE — the base class catch above already caught it!
    cout << "Specific: " << e.what();
}
// Always order catch blocks from MOST specific (derived) to LEAST specific (base) —
// otherwise a base-class catch silently swallows exceptions meant for a more specific handler.

4. Custom Exception Classes

For domain-specific errors, define your own exception class, typically deriving from std::exception (or a more specific standard type):

class InsufficientFundsException : public exception {
    private:
        string message;
    public:
        InsufficientFundsException(string msg) : message(msg) {}

        const char* what() const noexcept override {   // must match this exact signature
            return message.c_str();
        }
};

class BankAccount {
    private:
        double balance;
    public:
        BankAccount(double b) : balance(b) {}

        void withdraw(double amount) {
            if (amount > balance) {
                throw InsufficientFundsException("Withdrawal exceeds available balance");
            }
            balance -= amount;
        }
};

int main() {
    BankAccount acc(500);
    try {
        acc.withdraw(1000);
    } catch (const InsufficientFundsException &e) {
        cout << "Error: " << e.what() << endl;
    }
    return 0;
}

5. Stack Unwinding and Destructors

When an exception propagates up through function calls, all local objects in scopes it passes through are properly destructed (their destructors run) before the exception reaches its catch block — ensuring resources like memory or file handles are cleaned up correctly, provided your classes follow RAII (Module 2.2, formalized fully in Module 5.3). 

class Logger {
    public:
        Logger() { cout << "Logger created" << endl; }
        ~Logger() { cout << "Logger destroyed" << endl; }
};

void risky() {
    Logger log;                     // local object
    throw runtime_error("Oops");     // exception thrown — but log's destructor STILL runs during unwinding
}

int main() {
    try {
        risky();
    } catch (const exception &e) {
        cout << "Caught: " << e.what() << endl;
    }
    return 0;
}
// Output:
// Logger created
// Logger destroyed   ← runs automatically during stack unwinding, BEFORE the catch block executes
// Caught: Oops

6. The Danger of Raw Pointers with Exceptions

void risky() {
    int *data = new int[100];
    throw runtime_error("Oops");     // exception thrown BEFORE delete[] data; runs!
    delete[] data;                     // this line is NEVER REACHED — memory leak
}

This is precisely why modern C++ strongly prefers smart pointers (Module 5.3) over raw new/delete — a smart pointer's destructor runs automatically during stack unwinding (just like Logger above), safely freeing memory even when an exception is thrown mid-function.

Practice Questions

Conceptual

  1. Explain what happens, step by step, when an exception is thrown inside a function called from within a try block.
  2. Why must catch blocks for derived exception types be placed before catch blocks for their base types?
  3. What is stack unwinding, and why does it matter for objects that own resources (like dynamically allocated memory)?
  4. Why is throwing a raw int or C-string generally discouraged compared to throwing a standard exception type?
  5. What signature must a custom exception class's what() override exactly match, and why?

Coding

  1. Write a function double safeDivide(double a, double b) that throws a runtime_error if b == 0, and demonstrate catching it in main().
  2. Write a custom exception class NegativeValueException and use it inside a function that computes a square root, throwing it if the input is negative.
  3. Write a program with a try block containing multiple risky operations (array access, division, type conversion) and multiple catch blocks handling out_of_range, runtime_error, and a generic catch(...) fallback.
  4. Write a class Resource whose constructor prints "acquired" and destructor prints "released". Demonstrate that its destructor runs correctly even when an exception is thrown after the object is created but before the function returns normally.
