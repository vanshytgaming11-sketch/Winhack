Module 5.4 — Move Semantics

Move semantics, introduced in C++11, allow resources (like heap-allocated memory) to be transferred from one object to another WITHOUT copying the underlying data — instead, ownership is simply "stolen" from a temporary or explicitly-marked source object. This is one of modern C++'s most important performance features, and directly underlies how unique_ptr can be "moved but not copied" from Module 5.3.

1. Lvalues vs Rvalues

Every C++ expression is categorized as either an lvalue or an rvalue — this distinction is the foundation move semantics is built on.

CategoryMeaningExamples
LvalueHas a persistent identity/name — you can take its addressA named variable: x, arr[0], a dereferenced pointer *p
RvalueTemporary, about to be destroyed — no persistent identityA literal (5), the result of an expression (a + b), a temporary object (Student("X"))
 
int x = 10;        // x is an lvalue; 10 is an rvalue (a temporary literal)
int y = x + 5;         // x is an lvalue; (x + 5) is an rvalue — a temporary computed result

// A simple mental test: can you take its address with &?
&x;      // valid — x is an lvalue
&(x+5);   // COMPILE ERROR — (x+5) is a temporary rvalue with no persistent memory address

2. Rvalue References (&&)

C++11 introduced a new reference type, &&, that specifically binds ONLY to rvalues (temporaries) — this is the mechanism that lets a function distinguish "this argument is a temporary I can safely steal resources from" versus "this argument is a persistent object I must not modify destructively." 

int x = 10;

int &lref = x;          // regular lvalue reference — binds to the named variable x
// int &lref2 = 5;         // COMPILE ERROR — lvalue reference cannot bind to a temporary rvalue

int &&rref = 5;             // rvalue reference — CAN bind to a temporary
// int &&rref2 = x;            // COMPILE ERROR — rvalue reference cannot bind to a persistent lvalue

cout << rref;                     // 5 — the rvalue reference extends the temporary's lifetime, letting you use it

3. std::move

std::move(x) does NOT actually move anything by itself — it's simply a cast that converts an lvalue into an rvalue reference, signaling to the compiler (and to whichever function receives it) "treat this object as disposable; you may steal its internal resources rather than copying them." 

#include <utility>

string a = "Hello";
string b = std::move(a);   // b "steals" a's internal buffer instead of copying it — much faster for large strings

cout << b;                    // "Hello"
cout << a;                       // UNSPECIFIED — a is left in a "valid but unspecified" state after being moved from
                                    // (often empty for strings/vectors, but this is NOT guaranteed by the standard —
                                    // you should never rely on a moved-from object's specific value)

Critical rule: after moving from an object, you may still assign a new value to it or destroy it — but you must not rely on its current contents, since the standard only guarantees it's left in "some valid but unspecified state."

4. Move Constructor

A move constructor initializes a new object by "stealing" the resources (e.g., a heap pointer) from a temporary or explicitly-moved source object, rather than performing a deep copy (Module 2.3). It takes an rvalue reference parameter. 

class IntArray {
    public:
        int *data;
        int size;

        // Regular (deep) copy constructor — expensive, allocates new memory and copies every element
        IntArray(const IntArray &other) : size(other.size) {
            cout << "Copy constructor (expensive)" << endl;
            data = new int[size];
            for (int i = 0; i < size; i++) data[i] = other.data[i];
        }

        // Move constructor — cheap, just steals the pointer, no allocation or copying at all
        IntArray(IntArray &&other) noexcept : data(other.data), size(other.size) {
            cout << "Move constructor (cheap)" << endl;
            other.data = nullptr;   // CRITICAL — null out the source so its destructor doesn't free OUR stolen memory
            other.size = 0;
        }

        IntArray(int s) : size(s) {
            data = new int[size];
        }

        ~IntArray() {
            delete[] data;   // safe even if data is nullptr — delete on nullptr is a guaranteed no-op
        }
};

int main() {
    IntArray a(1000000);          // large array
    IntArray b = a;                    // COPY constructor — expensive, duplicates 1,000,000 ints
    IntArray c = std::move(a);            // MOVE constructor — cheap, just steals the pointer, O(1)

    return 0;
}

Why other.data = nullptr; is essential: without it, both c.data and the moved-from a.data would point to the SAME memory block — when both destructors eventually run, this becomes a double-free (exactly the shallow-copy bug from Module 2.3, but through a different mechanism). Nulling out the source prevents its destructor from freeing memory that's now owned elsewhere.

5. Move Assignment Operator

class IntArray {
    public:
        int *data;
        int size;

        // ... constructors as above ...

        // Move assignment operator
        IntArray& operator=(IntArray &&other) noexcept {
            if (this == &other) return *this;   // self-move-assignment guard

            delete[] data;              // free THIS object's existing resource first

            data = other.data;             // steal the pointer
            size = other.size;
            other.data = nullptr;             // null out the source
            other.size = 0;

            return *this;
        }
};

int main() {
    IntArray a(100), b(50);
    b = std::move(a);   // move ASSIGNMENT (b already exists) — steals a's memory, frees b's old memory first
    return 0;
}

6. Why noexcept Matters for Move Operations

Move constructors/assignment operators should be marked noexcept whenever possible. STL containers like vector check this: during a reallocation (Module 4.1/4.8), vector will only use the (fast) move constructor if it's guaranteed not to throw — otherwise, it falls back to the (slower but safer) copy constructor, since a failure mid-move could leave the vector in a corrupted, half-moved state with no way to safely roll back.

7. When Does the Compiler Automatically Choose Move Over Copy?

IntArray makeArray() {
    IntArray temp(100);
    return temp;   // temp is about to be destroyed anyway — compiler automatically MOVES it out
                       // (or elides the copy/move entirely — see Move & Copy Rules, Module 5.5)
}

int main() {
    IntArray a = makeArray();       // move constructor used (or elided) — NOT a full deep copy
    IntArray b(50);
    b = makeArray();                    // move ASSIGNMENT used — makeArray()'s return value is a temporary (rvalue)
    IntArray c = a;                        // COPY constructor used — a is a persistent lvalue, not a temporary
    return 0;
}

The compiler automatically prefers the move constructor/assignment whenever the source is an rvalue (a temporary, or something explicitly wrapped in std::move) — you only need std::move explicitly when working with a named variable (an lvalue) that you want to treat as disposable.

Practice Questions

Conceptual

  1. Explain the difference between an lvalue and an rvalue, with your own examples of each.
  2. What does std::move() actually do — and why is calling it, by itself, NOT the thing that performs the move?
  3. Why must a move constructor null out the source object's pointer after stealing it? What bug would occur if it didn't?
  4. Why do STL containers like vector require move constructors to be marked noexcept to actually use them during reallocation?
  5. Explain why an object should not be relied upon for its specific value after being moved from, even though it remains in a "valid" state.

Coding

  1. Implement a Buffer class managing a raw char*, with both a deep copy constructor and a move constructor. Add print statements in each to demonstrate which one gets called in different scenarios.
  2. Write a program demonstrating the performance difference conceptually: create a large IntArray, then time (or just annotate in comments) the difference between copying it and moving it.
  3. Implement a move assignment operator for a class managing a dynamically allocated array, including the self-move-assignment guard and correctly freeing the destination's prior resource.
  4. Write a function that returns a large object by value, and demonstrate (with print statements in the move constructor) that the compiler uses the move constructor rather than the copy constructor when the return value is assigned to a new variable.
