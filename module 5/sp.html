Module 5.3 — Smart Pointers

Modules 2.1 and 3.2 established the recurring dangers of raw new/delete: memory leaks, dangling pointers, double-frees, and resources leaked when an exception is thrown mid-function. Smart pointers solve all of these by wrapping a raw pointer inside a class that automatically manages its lifetime using RAII (Module 2.2) — the memory is freed automatically when the smart pointer goes out of scope, no matter how the function exits.

1. Why Smart Pointers — The Problem Restated

void riskyFunction() {
    int *p = new int(42);
    doSomethingThatMightThrow();  // if this throws, delete p below is NEVER reached — LEAK
    delete p;
}

Smart pointers eliminate this entire bug class by tying deallocation to the object's own destructor, which C++ guarantees runs during stack unwinding (Module 3.2) — regardless of whether the function returns normally or an exception propagates through it.

2. std::unique_ptr — Exclusive Ownership

A unique_ptr represents sole, exclusive ownership of a dynamically allocated object. Exactly one unique_ptr can own a given object at a time — it cannot be copied, only moved (Module 5.4). When it goes out of scope, it automatically deletes the object it owns. 

#include <memory>
using namespace std;

void demo() {
    unique_ptr<int> p = make_unique<int>(42);   // preferred way to create one (C++14+)
    cout << *p;                                    // 42 — dereference just like a raw pointer

    // No delete needed — p's destructor automatically frees the memory
    // when demo() returns, EVEN IF an exception is thrown before this point
}

Cannot Be Copied — Only Moved

unique_ptr<int> p1 = make_unique<int>(10);
// unique_ptr<int> p2 = p1;         // COMPILE ERROR — copy constructor is deleted; ownership must be UNIQUE

unique_ptr<int> p2 = move(p1);        // OK — transfers ownership from p1 to p2
cout << (p1 == nullptr);                 // true — p1 no longer owns anything after the move
cout << *p2;                                // 10 — p2 now owns it

This compile-time enforcement is the entire point: it's structurally impossible to accidentally have two owners of the same unique_ptr-managed memory, which eliminates double-free bugs by design.

Using unique_ptr with Arrays and Custom Classes

unique_ptr<int[]> arr = make_unique<int[]>(5);  // dynamically allocated array, auto-freed with delete[]
arr[0] = 10;
arr[1] = 20;

class Student {
    public:
        string name;
        Student(string n) : name(n) { cout << name << " created" << endl; }
        ~Student() { cout << name << " destroyed" << endl; }
};

unique_ptr<Student> s = make_unique<Student>("Vinit");
cout << s->name;   // -> works just like a raw pointer, for accessing members
// "Vinit destroyed" prints automatically when s goes out of scope

Passing unique_ptr to Functions

void takeOwnership(unique_ptr<int> p) {   // by value — takes ownership, caller loses it
    cout << *p;
}   // p is destroyed here, memory freed

void justUse(const unique_ptr<int> &p) {   // by const reference — caller RETAINS ownership
    cout << *p;
}

int main() {
    unique_ptr<int> p = make_unique<int>(42);
    justUse(p);                                 // p is still valid afterward
    takeOwnership(move(p));                        // MUST explicitly move — p is now null afterward
    cout << (p == nullptr);                            // true
    return 0;
}

3. std::shared_ptr — Shared Ownership

A shared_ptr allows multiple pointers to jointly own the same object, using internal reference counting — the object is only deleted once the LAST shared_ptr owning it is destroyed or reset. 

#include <memory>
using namespace std;

void demo() {
    shared_ptr<int> p1 = make_shared<int>(42);
    cout << p1.use_count();     // 1 — one owner

    {
        shared_ptr<int> p2 = p1;    // COPY is allowed — both now share ownership
        cout << p1.use_count();       // 2 — reference count incremented
        cout << *p2;                     // 42
    } // p2 goes out of scope here — reference count decrements back to 1, memory NOT freed yet

    cout << p1.use_count();     // 1 — back down, p1 still owns it
} // p1 goes out of scope — reference count hits 0 — memory IS finally freed here

How Reference Counting Works

Internally, a shared_ptr maintains a shared "control block" (allocated once, shared by all copies) tracking the current reference count. Every time a shared_ptr is copied, the count increments; every time one is destroyed or reset, the count decrements. When the count reaches zero, the managed object is deleted automatically. 

shared_ptr<int> p1 = make_shared<int>(100);
shared_ptr<int> p2 = p1;
shared_ptr<int> p3 = p2;

cout << p1.use_count();   // 3 — all three share ownership of the SAME object

p2.reset();                   // p2 releases its ownership — count drops to 2
cout << p1.use_count();          // 2

4. The Circular Reference Problem

shared_ptr has one significant pitfall: if two objects hold shared_ptrs to each other, their reference counts never reach zero — even if nothing else in the program references them — causing a memory leak despite using "smart" pointers. 

class B; // forward declaration

class A {
    public:
        shared_ptr<B> bPtr;
        ~A() { cout << "A destroyed" << endl; }
};

class B {
    public:
        shared_ptr<A> aPtr;
        ~B() { cout << "B destroyed" << endl; }
};

int main() {
    shared_ptr<A> a = make_shared<A>();
    shared_ptr<B> b = make_shared<B>();
    a->bPtr = b;    // A holds a shared_ptr to B
    b->aPtr = a;      // B holds a shared_ptr to A — CIRCULAR REFERENCE

    return 0;
    // Neither "A destroyed" nor "B destroyed" ever prints!
    // a's use_count is 2 (main's `a` + b's `aPtr`), b's use_count is 2 (main's `b` + a's `bPtr`)
    // Even though main()'s local a and b go out of scope, each object still has ONE remaining
    // reference from the OTHER object — neither count ever reaches zero. LEAKED.
}

5. std::weak_ptr — Breaking Circular References

A weak_ptr is a non-owning observer of an object managed by a shared_ptr — it does NOT increment the reference count, so it doesn't keep the object alive by itself. This is exactly the tool used to break circular reference cycles. 

class B; // forward declaration

class A {
    public:
        shared_ptr<B> bPtr;
        ~A() { cout << "A destroyed" << endl; }
};

class B {
    public:
        weak_ptr<A> aPtr;    // CHANGED to weak_ptr — does not contribute to A's reference count
        ~B() { cout << "B destroyed" << endl; }
};

int main() {
    shared_ptr<A> a = make_shared<A>();
    shared_ptr<B> b = make_shared<B>();
    a->bPtr = b;
    b->aPtr = a;    // weak_ptr assignment — does NOT increase A's use_count

    return 0;
    // Now BOTH destructors run correctly:
    // "A destroyed"
    // "B destroyed"
    // Because a's use_count correctly reaches 0 once main()'s `a` and A::bPtr chain are gone —
    // B's weak reference to A never counted toward keeping A alive.
}

Using a weak_ptr's Value — .lock()

Since the object a weak_ptr observes might already be destroyed, you can't dereference it directly — you must call .lock(), which returns a temporary shared_ptr (or an empty one if the object no longer exists): 

shared_ptr<int> sp = make_shared<int>(42);
weak_ptr<int> wp = sp;

if (shared_ptr<int> locked = wp.lock()) {   // succeeds — sp is still alive
    cout << *locked;                            // 42
}

sp.reset();   // the only shared_ptr owner releases the object — it's now destroyed

if (shared_ptr<int> locked = wp.lock()) {
    cout << *locked;
} else {
    cout << "Object no longer exists" << endl;   // this runs — wp correctly detects the object is gone
}

6. RAII — The Underlying Principle (formal recap)

Smart pointers are a direct, general-purpose application of the RAII pattern first introduced in Module 2.2: "Resource Acquisition Is Initialization" — a resource (here, heap memory) is acquired in a constructor and automatically released in a destructor, tying its lifetime directly to a scope. This is precisely why smart pointers require no manual cleanup and remain safe even when exceptions are thrown mid-function.

7. Ownership Model — When to Use Which

Smart pointerOwnership modelUse when
unique_ptrExclusive — exactly one ownerDefault choice. Use unless you specifically need shared ownership
shared_ptrShared — multiple owners, reference-countedMultiple parts of code genuinely need to jointly own/extend an object's lifetime
weak_ptrNon-owning observerBreaking circular shared_ptr references; observing an object without extending its lifetime

Modern C++ guideline: avoid raw new/delete in application code entirely — default to unique_ptr, and reach for shared_ptr only when genuine shared ownership is required.
