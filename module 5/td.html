Module 5.1 — Type Deduction

C++11 introduced auto and decltype, letting the compiler infer a variable's type automatically instead of requiring it to be spelled out explicitly. This isn't "dynamic typing" — the type is still fixed and checked at compile time; only the spelling of the type is deferred to the compiler.

1. auto — Basics

auto x = 10;          // int — deduced from the literal
auto y = 3.14;           // double
auto z = 'A';               // char
auto s = string("Hi");         // string
auto b = true;                    // bool

// The type is deduced ONCE, at declaration, from the initializer — it does NOT change later
auto n = 5;
// n = "hello";   // COMPILE ERROR — n is permanently int, auto is not dynamic typing

auto requires an initializer — the compiler needs something to deduce the type FROM:

auto x;        // COMPILE ERROR — no initializer, nothing to deduce from
auto x = 10;     // OK

2. Why auto Matters — Verbose Types

auto's biggest practical value is avoiding painfully long, hard-to-read type names — especially with iterators and nested templates: 

// Without auto — verbose and error-prone to type out
std::map<std::string, std::vector<int>>::iterator it = myMap.begin();

// With auto — identical behavior, far more readable
auto it = myMap.begin();

// Another common case
vector<pair<int, string>> data;
for (auto it = data.begin(); it != data.end(); ++it) { ... }   // vs the fully spelled-out iterator type

3. auto with References and Const

By default, auto deduces a value type — it strips off & (reference) and top-level const from the initializer's type unless you explicitly ask for them. 

int x = 10;
const int &ref = x;

auto a = ref;          // int — auto STRIPS both const and & by default; a is a COPY, mutable
auto &b = ref;           // const int& — explicitly adding & preserves the reference (and its const-ness)
const auto &c = ref;      // const int& — explicit, most defensive form

a = 100;                     // fine — a is an independent copy, doesn't affect x
// b = 100;                    // COMPILE ERROR — b is const int&, inherited const-ness from ref
cout << x;                        // still 10 either way, since only `a` (a copy) was changed

This matters enormously in range-based for loops:

vector<int> v = {1, 2, 3, 4, 5};

for (auto x : v) {          // x is a COPY of each element — modifying x does NOT modify v
    x *= 2;                    // has no effect on v's actual contents
}
cout << v[0];                     // still 1

for (auto &x : v) {              // x is a REFERENCE — modifying x DOES modify v
    x *= 2;
}
cout << v[0];                        // 2 — v was actually modified

for (const auto &x : v) {              // x is a const reference — no copy made, but also can't modify
    cout << x << " ";                       // BEST PRACTICE for large objects you only need to read
}

Rule of thumb: use auto & when you intend to modify elements in place, const auto & when you only need to read (avoids unnecessary copies, especially important for large objects like string or custom classes), and plain auto only when you genuinely want an independent copy.

4. auto with Function Return Types (C++14+)

auto add(int a, int b) {   // return type deduced from the return statement — C++14+
    return a + b;              // deduced as int
}

auto multiply(double a, double b) {
    return a * b;                // deduced as double
}

If a function has multiple return statements, all of them must deduce to the exact same type, or it's a compile error.

5. Common auto Pitfalls

vector<int> v = {1, 2, 3};
auto size = v.size();   // size is deduced as size_t (unsigned!), NOT int

int diff = size - 5;      // if size is small, this can UNDERFLOW (wraps to a huge positive number)
                              // because size_t is unsigned — the same trap from Module 1.1!

// auto can silently deduce a type you didn't expect:
auto half = 5 / 2;        // int division → half = 2, NOT 2.5, even though "half" suggests a fraction

6. decltype

decltype(expr) yields the exact, unmodified type of an expression, WITHOUT evaluating it — unlike auto, it preserves references and const-ness exactly as they appear in the expression's declared type. 

int x = 10;
int &ref = x;
const int cx = 20;

decltype(x) a = 5;           // int — same type as x
decltype(ref) b = x;           // int& — decltype PRESERVES the reference-ness, unlike auto
decltype(cx) c = 30;              // const int — preserves const-ness too

auto vs decltype — The Key Difference

int x = 10;
int &ref = x;

auto a = ref;         // int  — auto strips the reference; a is a NEW independent copy
decltype(ref) b = x;    // int& — decltype preserves the reference exactly; b IS an alias for x

a = 999;                  // does NOT affect x
b = 999;                    // DOES affect x, because b is genuinely a reference to it
cout << x;                     // 999 — changed via b, unaffected by a

decltype for Generic/Template Code

decltype is especially useful in template code where you need to declare a variable of "whatever type this expression produces," without knowing that type in advance: 

template <typename T1, typename T2>
auto add(T1 a, T2 b) -> decltype(a + b) {   // trailing return type — needed pre-C++14
    return a + b;
}
// The return type is deduced as "whatever type a+b naturally produces" —
// e.g., int+double naturally produces double, and decltype(a+b) captures that automatically.

int main() {
    cout << add(3, 4.5);   // 7.5 — return type correctly deduced as double
    return 0;
}

In modern C++14+, this specific pattern is largely superseded by plain auto return type deduction (section 4 above) for simple cases — but decltype remains essential whenever exact type preservation (references, const-ness) genuinely matters.
