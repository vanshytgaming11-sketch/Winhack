Module 4.5 — Unordered Associative Containers

unordered_set and unordered_map provide the same key-based interface as set/map, but are implemented using a hash table instead of a balanced tree. This trades away sorted ordering for significantly faster average-case performance — O(1) average instead of O(log n).

1. std::unordered_set

#include <unordered_set>
using namespace std;

unordered_set<int> us;

us.insert(30);
us.insert(10);
us.insert(20);
us.insert(10);   // duplicate — ignored, just like set

for (int x : us) cout << x << " ";  // order is UNSPECIFIED — could print in any order,
                                          // NOT guaranteed to be 10 20 30 like std::set would be

cout << us.count(20);   // 1
us.erase(20);

auto it = us.find(30);
if (it != us.end()) cout << "Found: " << *it;

2. std::unordered_map

#include <unordered_map>
using namespace std;

unordered_map<string, int> ages;

ages["Vinit"] = 22;
ages["Aman"] = 20;
ages.insert({"Priya", 21});

for (auto &entry : ages) {
    cout << entry.first << ": " << entry.second << endl;
    // order is UNSPECIFIED — do not rely on any particular sequence
}

cout << ages["Vinit"];         // 22 — same auto-insert-on-read gotcha as std::map applies here too!
cout << ages.count("Aman");      // 1

3. map/set vs unordered_map/unordered_set — The Critical Interview Comparison

Aspectmap / setunordered_map / unordered_set
Internal structureSelf-balancing BST (Red-Black Tree)Hash table
OrderingAlways sorted by keyUnspecified / arbitrary
Average time complexityO(log n) for insert/find/eraseO(1) for insert/find/erase
Worst-case time complexityO(log n) — guaranteed, always balancedO(n) — if many keys collide into the same bucket
Memory overheadTree node pointers (typically 3 per node)Hash table buckets, generally comparable or higher
RequiresKeys must support < (or a custom comparator)Keys must support == and have a hash function
Use whenYou need sorted iteration, or range queries (lower_bound etc.)You only care about existence/lookup speed, order doesn't matter

4. Why Worst-Case O(n) Can Happen (Hash Collisions)

A hash table works by computing a hash of the key and using it to determine which "bucket" to store the element in. If many different keys happen to hash to the same bucket (a collision), that bucket internally degrades toward a linked list, and operations on it become O(bucket size) rather than O(1). With a well-designed hash function and a reasonable load factor, this is rare in practice — but it's why the standard guarantees only O(1) average, not O(1) worst-case. 

unordered_map<int, int> m;
cout << m.load_factor();     // average number of elements per bucket
cout << m.bucket_count();      // current number of buckets
m.rehash(100);                    // manually request at least 100 buckets — reduces collision likelihood

5. Custom Types as Keys

set/map only require the key type to support operator< (which most built-in types and std::string already do). unordered_set/unordered_map require both a hash function (std::hash<T>) and an equality check (operator==) — this is why using a custom struct/class as a key in an unordered container requires extra setup that ordered containers don't: 

struct Point {
    int x, y;
    bool operator==(const Point &other) const {
        return x == other.x && y == other.y;
    }
};

// Must provide a custom hash specialization for unordered_set/unordered_map to work with Point:
struct PointHash {
    size_t operator()(const Point &p) const {
        return hash<int>()(p.x) ^ (hash<int>()(p.y) << 1);
    }
};

unordered_set<Point, PointHash> points;
points.insert({1, 2});
points.insert({3, 4});

For a std::set<Point> instead, you'd only need to define operator< on Point — a simpler requirement, which is one reason ordered containers are sometimes preferred for custom types despite the performance trade-off.

6. When to Choose Which

  • Default to unordered_map/unordered_set when you only need fast lookups/insertions and don't care about order — this covers the vast majority of DSA interview problems (frequency counting, seen-before checks, deduplication).
  • Use map/set when you need sorted iteration, range queries (lower_bound/upper_bound), or predictable worst-case guarantees (important in real-time/latency-sensitive systems where an occasional O(n) hash collision spike would be unacceptable).

Practice Questions

Conceptual

  1. Explain the core structural difference between map and unordered_map that leads to their different time complexities.
  2. Why does unordered_map have O(1) average but O(n) worst-case complexity? What causes the worst case?
  3. Why can't you directly use a custom struct as a key in an unordered_set without extra work, while a set only needs operator< defined?
  4. Give two concrete scenarios: one where unordered_map is clearly the better choice, and one where map is clearly better, with reasoning.

Coding

  1. Write a program that uses unordered_set to check for duplicate elements in an array in O(n) average time.
  2. Write a program that uses unordered_map<int,int> to solve the "two sum" problem: given an array and a target, find two indices whose values sum to the target, in a single pass.
  3. Write a program that counts word frequency in a paragraph using unordered_map<string,int>, then separately prints the same result sorted alphabetically (requiring a copy into a map or a sort step) — to demonstrate the ordering trade-off directly.
  4. Write a program defining a custom struct Employee {int id; string name;} with a custom hash function, and demonstrate storing/looking up Employee objects in an unordered_set.
