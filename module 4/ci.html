Module 4.8 — Complexity & Internals

This module consolidates the internal implementation of every STL container covered so far — the "why" behind each container's time complexities from Modules 4.1–4.5. Interviewers frequently ask "how is X implemented internally, and why does that give it O(?) complexity for operation Y" — this is your single reference for that entire class of question.

1. vector → Dynamic Array

Internally a single contiguous block of heap memory, plus a tracked size (elements in use) and capacity (total allocated space). When size would exceed capacity, a NEW, larger block is allocated (commonly double the old capacity), all existing elements are copied/moved into it, and the old block is freed.

OperationComplexityWhy
Random access v[i]O(1)Direct address computation: base + i * sizeof(T)
push_backO(1) amortizedUsually just writes to the next free slot; occasionally triggers an O(n) reallocation, averaged out over many calls
Insert/erase at front or middleO(n)All subsequent elements must shift to fill/make the gap
pop_backO(1)Just decrements size — no shifting needed

2. deque → Block/Chunk Storage (Segmented Array)

Implemented as multiple fixed-size chunks of contiguous memory, tracked via an internal "map" array of pointers to each chunk. This indirection is what allows both ends to grow independently in O(1) — a new chunk can be allocated at either end without touching or moving any existing elements.

OperationComplexityWhy
Random access dq[i]O(1)Two-step lookup (find chunk, then offset within it) — still constant time, just slightly slower constant than vector
push_front / push_backO(1)New chunks are allocated at either end independently — no shifting of existing chunks
Insert/erase in the middleO(n)Still requires shifting elements within/across chunks

3. list → Doubly Linked List

Each element is an individually heap-allocated node containing the value plus prev and next pointers. There is no contiguous memory and no way to jump to an arbitrary index without traversing node by node.

OperationComplexityWhy
Random accessNot supported (would be O(n) if manually traversed)No index-to-address formula exists — must follow pointers one by one
Insert/erase given an iterator/positionO(1)Only a few pointers need relinking — no data shifting
Search for a valueO(n)Must traverse from an end, checking each node

4. set / map → Self-Balancing Binary Search Tree (Red-Black Tree)

Elements are stored as nodes in a Red-Black Tree — a binary search tree that automatically re-balances itself after every insertion/deletion, guaranteeing the tree's height stays O(log n) regardless of insertion order (unlike a plain unbalanced BST, which can degrade to O(n) height in the worst case, e.g., inserting already-sorted data).

OperationComplexityWhy
Insert / Erase / FindO(log n) — guaranteed, every timeTree height is kept balanced at O(log n) via rotation rules after every modification
In-order traversal (i.e., iterating the container)O(n), always in sorted orderA binary search tree's in-order traversal visits nodes in ascending key order by definition

Why this guarantees sorted iteration: the BST invariant (left subtree < node < right subtree) means an in-order traversal (left → node → right, recursively) always visits nodes in ascending order — this is exactly why set/map iteration is always sorted, with zero extra sorting cost.

5. unordered_set / unordered_map → Hash Table

Elements are distributed across an array of "buckets," with each element's bucket determined by hash(key) % bucket_count. Multiple elements landing in the same bucket (a collision) are typically chained together in a small linked list within that bucket.

OperationAverage complexityWorst-case complexityWhy
Insert / Erase / FindO(1)O(n)Average case: hash spreads elements evenly, each bucket has ~1 element. Worst case: all elements collide into one bucket, degrading to a linked-list scan

As more elements are inserted, the load factor (elements ÷ buckets) rises; once it crosses a threshold, the table automatically rehashes — allocates more buckets and redistributes all elements — to keep the average bucket size small and operations close to O(1).

6. priority_queue → Binary Heap

Internally, a priority_queue is a vector maintained in a special order satisfying the heap property: every parent node is ≥ (max-heap) or ≤ (min-heap) both its children. This is stored implicitly in a flat array — for a node at index i, its children are at indices 2i+1 and 2i+2, and its parent is at (i-1)/2 — no explicit tree pointers needed at all.

OperationComplexityWhy
top()O(1)The max (or min) element is always maintained at the root — index 0
push()O(log n)New element is added at the end, then "bubbled up" (swapped with its parent repeatedly) until the heap property is restored
pop()O(log n)Root is removed, the last element is moved to the root, then "sifted down" until the heap property is restored

This structure is explored in full algorithmic depth in Module 6.7 (Heaps).

Practice Questions

Conceptual

  1. Explain why a vector's push_back is amortized O(1) but inserting at the front is O(n).
  2. Why does a Red-Black Tree guarantee O(log n) operations, while a plain (unbalanced) BST could degrade to O(n)? What specifically causes an unbalanced BST to degrade, and with what input?
  3. Explain, using the parent/child index formulas, why a binary heap can be efficiently represented in a flat array instead of using explicit tree node pointers.
  4. Why does unordered_map have O(1) average but O(n) worst-case complexity, while map has a guaranteed O(log n) in all cases? In what scenario might you prefer the guaranteed bound over the better average case?
  5. Explain why in-order traversal of a BST always yields sorted output, and how this directly explains set/map iteration behavior.

Applied

  1. Given a use case requiring 100,000 random-access reads and only 10 insertions at the end, justify which sequence container is optimal and why.
  2. Given a use case requiring frequent insertions/removals from both the front and back but no random access needed, justify the best container choice.
  3. Given a use case requiring fast membership testing with no need for sorted output, justify choosing unordered_set over set, and describe one scenario where you'd choose set instead despite the performance cost.
  4. Explain, step by step, what happens internally when priority_queue::push() is called on a max-heap containing {50, 30, 40, 10, 20} and the value 60 is pushed.
