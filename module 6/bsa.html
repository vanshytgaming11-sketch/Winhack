Module 6.14 — Binary Search on Answer

Module 4.7 covered binary_search for finding a value directly within a sorted array. This module covers a more advanced application: binary searching over a range of possible answers to an optimization problem, even when no explicit sorted array exists — as long as the underlying feasibility condition is monotonic.

1. The Core Idea — Search the Answer Space, Not the Data

Instead of asking "is X in this array," this pattern asks "what is the smallest/largest value X such that condition(X) is true," where checking condition(X) for any single candidate X is efficient, and the condition is monotonic — once it becomes true (or false), it stays that way for all larger values. 

Example monotonic pattern:
condition(X):  false false false true true true true true
                                  ^
                            the answer we want — the FIRST X where it becomes true

This shape (a clean flip from false to true) is EXACTLY what binary search requires —
it doesn't matter that X isn't an array index; it's a candidate VALUE in a search space.

2. The General Template

int binarySearchOnAnswer(int lo, int hi) {
    while (lo < hi) {
        int mid = lo + (mid - lo) / 2;  // placeholder — see the corrected version below
        if (isFeasible(mid)) {
            hi = mid;        // mid works — try to find an even BETTER (smaller) answer
        } else {
            lo = mid + 1;      // mid doesn't work — need a LARGER value
        }
    }
    return lo;   // lo == hi — the smallest value for which isFeasible() is true
}
// Corrected — proper midpoint computation:
int binarySearchOnAnswer(int lo, int hi) {
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;   // avoids potential overflow compared to (lo+hi)/2
        if (isFeasible(mid)) {
            hi = mid;
        } else {
            lo = mid + 1;
        }
    }
    return lo;
}

Why lo + (hi - lo) / 2 instead of (lo + hi) / 2: if lo and hi are both large, their sum could overflow int's range before the division happens — this rewritten form avoids that risk entirely, a detail worth mentioning explicitly in an interview.

3. Classic Example — "Minimize the Maximum" — Split Array Largest Sum

Given an array and a number of subarrays K, split the array into K contiguous parts to MINIMIZE the largest sum among the parts.

bool canSplit(vector<int> &nums, int k, long maxSum) {
    int subarrays = 1;
    long currentSum = 0;

    for (int num : nums) {
        if (currentSum + num > maxSum) {   // adding this element would exceed the cap — start a NEW subarray
            subarrays++;
            currentSum = num;
            if (subarrays > k) return false;   // used too many subarrays — this maxSum is TOO SMALL to work
        } else {
            currentSum += num;
        }
    }
    return true;   // successfully split into k or fewer subarrays, respecting the cap
}

int splitArray(vector<int> &nums, int k) {
    long lo = *max_element(nums.begin(), nums.end());   // the answer can't be smaller than the LARGEST single element
    long hi = accumulate(nums.begin(), nums.end(), 0L);    // the answer can't be larger than the TOTAL sum (k=1 case)

    while (lo < hi) {
        long mid = lo + (hi - lo) / 2;   // mid = a CANDIDATE maximum-subarray-sum cap

        if (canSplit(nums, k, mid)) {
            hi = mid;         // this cap WORKS — try to find a smaller (better) cap
        } else {
            lo = mid + 1;        // this cap is TOO SMALL — need a larger one
        }
    }
    return lo;
}
// O(n log(sum)) time — canSplit() is O(n), called O(log(range of possible sums)) times
// This is DRAMATICALLY better than trying every possible split combination directly,
// which would be combinatorially expensive

Why This Is Monotonic (the key justification)

If a maximum-sum cap of X allows a valid split into ≤ K subarrays, then ANY larger cap X' > X also allows a valid split (it's strictly easier — more room per subarray). This monotonic "once true, always true for larger values" property is exactly what makes binary search on the answer valid here.

4. Another Classic — Koko Eating Bananas (Minimum Feasible Rate)

bool canFinish(vector<int> &piles, int speed, int hours) {
    long totalHours = 0;
    for (int pile : piles) {
        totalHours += (pile + speed - 1) / speed;   // ceiling division — hours needed for this pile at this speed
    }
    return totalHours <= hours;
}

int minEatingSpeed(vector<int> &piles, int hours) {
    int lo = 1;                                       // slowest conceivable speed
    int hi = *max_element(piles.begin(), piles.end());  // no need to eat faster than the largest single pile

    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;   // candidate eating speed

        if (canFinish(piles, mid, hours)) {
            hi = mid;         // this speed WORKS — try a slower (smaller) speed
        } else {
            lo = mid + 1;        // too slow — need to eat FASTER
        }
    }
    return lo;
}
// O(n log(max pile size)) time — same structural pattern as splitArray above:
// binary search over the CANDIDATE ANSWER (eating speed), with an O(n) feasibility check per candidate

5. Recognizing This Pattern — Signal Checklist

  • The problem asks to "minimize the maximum" or "maximize the minimum" of something.
  • There's a clear, checkable feasibility function: "can this specific candidate value work?"
  • The feasibility function is monotonic across the range of possible answers.
  • A brute-force approach would mean testing every possible answer value one by one, each requiring its own O(n) check — binary search reduces this to O(log(range)) checks instead.

6. Comparing to Standard Binary Search (Module 4.7)

AspectStandard binary searchBinary search on answer
Searches overA sorted ARRAY of existing valuesAn ABSTRACT range of candidate answer values

What's returnedAn index or boolean (found/not found)The optimal answer value itself

Conceptual

  2. Why is lo + (hi - lo) / 2 preferred over (lo + hi) / 2 for computing the midpoint?
  3. In the Split Array problem, explain why lo is initialized to the array's maximum element and hi to the total sum — why are these the correct bounds?
  4. Compare standard binary search (on a sorted array) to binary search on answer — what's the same about their core loop structure, and what's fundamentally different?
  5. What signal in a problem statement should make you consider this pattern over a more direct approach?

Coding

  1. Write a function to find the square root of a non-negative integer using binary search on answer (without using sqrt()), returning the floor of the actual square root.

  3. Write a function to find the minimum number of days needed to make M bouquets from a garden of flowers that bloom on given days, where each bouquet requires K adjacent already-bloomed flowers.
  4. Write a function to find the K-th smallest element in a sorted matrix (rows and columns both sorted) using binary search on the value range, rather than a heap-based approach.
