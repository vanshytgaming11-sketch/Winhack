Module 6.1 — Complexity Analysis

Every DSA topic from here forward is evaluated by its time and space complexity — this module formalizes the notation and reasoning you'll apply throughout Module 6. If Modules 1–5 were about writing correct C++, Module 6 is about writing efficient C++, and complexity analysis is the language used to reason about efficiency precisely.

1. What Is Big-O Notation?

Big-O describes how an algorithm's running time (or memory usage) grows as the input size n grows large — it captures the growth rate, deliberately ignoring constant factors and lower-order terms, because those become irrelevant compared to the dominant term as n gets large. 

// This loop does exactly n iterations — its time complexity is O(n)
for (int i = 0; i < n; i++) {
    cout << i;
}

// This does 3n + 5 operations, but Big-O DROPS constants and lower-order terms:
for (int i = 0; i < n; i++) {
    cout << i;      // n times
    cout << i * 2;   // n times
    cout << i * 3;   // n times
}
cout << "done" << endl; // +5 fixed operations
// Total: 3n + 5 operations — but this is STILL described as O(n), not O(3n+5),
// because as n grows huge, the constant factor 3 and the +5 become insignificant
// compared to the fact that work scales LINEARLY with n.

2. Common Complexity Classes (from best to worst)

NotationNameExample
O(1)ConstantArray access by index, hash map lookup (average case)
O(log n)LogarithmicBinary search, balanced BST operations
O(n)LinearSingle loop through an array, linear search
O(n log n)LinearithmicEfficient sorting (merge sort, quicksort average case)
O(n²)QuadraticNested loops over the same input, bubble sort
O(2ⁿ)ExponentialNaive recursive Fibonacci, generating all subsets
O(n!)FactorialGenerating all permutations, brute-force traveling salesman

Visualizing Growth Rates

n = 10:
  O(1)       = 1
  O(log n)   ≈ 3
  O(n)       = 10
  O(n log n) ≈ 33
  O(n²)      = 100
  O(2ⁿ)      = 1024

n = 20:
  O(1)       = 1
  O(log n)   ≈ 4
  O(n)       = 20
  O(n log n) ≈ 86
  O(n²)      = 400
  O(2ⁿ)      = 1,048,576   ← already exploding at n=20!

This is why exponential algorithms are only practical for very small inputs — the naive recursive Fibonacci from Module 1.3 becomes unusably slow well before n reaches 40.

3. Determining Complexity — Rules of Thumb

Sequential statements — ADD complexities

for (int i = 0; i < n; i++) { ... }   // O(n)
for (int i = 0; i < n; i++) { ... }     // O(n)
// Total: O(n) + O(n) = O(2n) = O(n)  — constants dropped

Nested loops (over the same input) — MULTIPLY complexities

for (int i = 0; i < n; i++) {
    for (int j = 0; j < n; j++) {
        cout << i * j;
    }
}
// Outer loop: n iterations. Inner loop: n iterations EACH TIME.
// Total: n * n = O(n²)

Independent (non-nested) loops over different inputs — ADD, don't multiply

for (int i = 0; i < n; i++) { ... }    // O(n)
for (int j = 0; j < m; j++) { ... }      // O(m) — a DIFFERENT input size
// Total: O(n + m) — NOT O(n * m), since these are sequential, not nested

Loop with a shrinking/growing step — often logarithmic

int i = n;
while (i > 1) {
    i = i / 2;   // halves each time — how many times can you halve n before reaching 1?
    cout << i;
}
// Total: O(log n) — the number of halvings needed to go from n down to 1

Recursive calls — analyze via the recursion tree

int factorial(int n) {
    if (n <= 1) return 1;
    return n * factorial(n - 1);
}
// One recursive call per level, n levels deep → O(n)

int fib(int n) {
    if (n <= 1) return n;
    return fib(n-1) + fib(n-2);
}
// TWO recursive calls per level → the call tree branches exponentially → O(2^n)

4. Best, Average, and Worst Case

Many algorithms have different complexities depending on the specific input, not just its size. Big-O by convention usually refers to the worst case unless stated otherwise, but distinguishing all three matters for real interview discussions.

CaseMeaningExample — Linear Search
Best caseThe most favorable input — fastest possible runTarget is the FIRST element checked → O(1)
Average caseExpected performance over typical/random inputsTarget is somewhere in the middle, on average → O(n/2) → simplifies to O(n)
Worst caseThe most unfavorable input — slowest possible runTarget is the LAST element, or absent entirely → O(n)

A Concrete Example — Quicksort

Best/Average case:  O(n log n)  — pivot splits the array roughly in half each time
Worst case:          O(n²)        — pivot is always the smallest/largest element
                                      (e.g., an already-sorted array with a naive pivot choice),
                                      causing maximally unbalanced partitions every time

This exact best-vs-worst-case gap is why quicksort's pivot selection strategy matters in practice, and why some libraries use hybrid approaches (like introsort, mentioned in Module 4.7) to guard against worst-case inputs.

5. Space Complexity

Alongside time, algorithms are also measured by how much extra memory they use relative to input size (not counting the input itself, which is a fixed cost regardless of algorithm choice). 

// O(1) space — uses a fixed, constant amount of extra memory regardless of n
int sum(vector<int> &v) {
    int total = 0;
    for (int x : v) total += x;
    return total;
}

// O(n) space — allocates memory proportional to n
vector<int> doubleAll(vector<int> &v) {
    vector<int> result;
    for (int x : v) result.push_back(x * 2);
    return result;
}

// O(n) space from the CALL STACK — recursion depth grows linearly with n (Module 1.3)
int factorial(int n) {
    if (n <= 1) return 1;
    return n * factorial(n - 1);   // n stack frames exist simultaneously at maximum depth
}

There is frequently a time-space trade-off: using extra memory (like a hash map for O(1) lookups, or memoization in DP — Module 6.10) often reduces time complexity significantly, at the cost of additional space.

6. Why This Matters for Interviews

Every problem in Modules 6.2 onward will explicitly discuss the complexity of each approach — interviewers consistently expect you to state and justify the time/space complexity of any solution you propose, and to recognize when a brute-force O(n²) approach can be improved to O(n log n) or O(n) using better data structures or algorithmic patterns.

Practice Questions

Conceptual

  1. Why does Big-O notation drop constant factors and lower-order terms? Give an example where this simplification could mislead someone comparing two algorithms for small inputs.
  2. Explain why nested loops over the same input multiply their complexities, while sequential loops add them.
  3. Why is quicksort's average case O(n log n) but its worst case O(n²)? What specific input triggers the worst case with a naive pivot strategy?
  4. Explain the time-space trade-off with a concrete example (other than memoization) where using more memory reduces time complexity.
  5. Why does recursion generally have O(depth) space complexity, even if no extra data structure is explicitly allocated inside the function?

Analyze the Complexity

  1. for (int i = 0; i < n; i++) {
    for (int j = i; j < n; j++) {
        cout << i << j;
    }
}
    What is the time complexity? (Hint: it's not simply O(n²), though it IS still that order — explain why the inner loop's changing range doesn't change the overall class.) 
  2. for (int i = 1; i < n; i *= 2) {
    cout << i;
}
  3. void mystery(int n) {
    if (n <= 0) return;
    cout << n;
    mystery(n / 2);
    mystery(n / 2);
}
    (Hint: draw the recursion tree — how many levels, and how many calls per level?)

Coding

  1. Write two different implementations of a function checking whether an array contains duplicates: one O(n²) brute-force version (nested loops), and one O(n) version using a set. State each one's time and space complexity in a comment.
  2. Write a recursive function to compute the sum of digits of a number, and state its time complexity in terms of the number of digits.
